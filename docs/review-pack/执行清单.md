## 一、先记住项目定位

一句话版本：

> Page 是一个本地 Coding Agent Runtime。它在工具执行前后记录状态，任务中断后先核对真实文件，再安全地继续执行。

主亮点是 Recovery，不是功能数量。

恢复机制要证明 5 件事：

1. 文件已经改完但 Checkpoint 还没保存时，不会重复修改。
2. 工具还没执行时，可以安全重试。
3. 文件被外部修改后，旧摘要和旧读取结果不能继续使用。
4. 工作区、工具签名或数据版本不一致时，拒绝盲目恢复。
5. 每个决定都能在 Journal、Hash 和 Trace 中找到证据，不让模型猜底层状态。

辅助亮点是 freshness-aware Context：上下文里的文件信息带来源和 Hash，过期后会被拒绝；系统还能解释每段内容为什么保留、压缩或删除。

Memory 仍然存在，但不是本轮主角。面试前不再增加向量库、Embedding、重排或知识图谱。

## 二、必须记住的实验结果

### FakeModel

- 3 个任务分别运行 blind 和 guarded 两种模式；
- 两组 verifier 都是 3/3；
- guarded 确定性跳过了 2 次重复文件动作；
- Journal 中实际写动作从 3 次降到 2 次；
- guarded 识别了 1 次 stale 状态。

FakeModel 的作用是稳定验证状态机，不是测试模型理解能力。

### DeepSeek

实验规模：

```text
3 个任务 × 2 种模式 × 2 次重复 = 12 次任务运行
```

结果：

| 指标 | blind | guarded |
| --- | ---: | ---: |
| 成功任务 | 4/6 | 6/6 |
| 模型请求 | 25 | 22 |
| 工具步骤 | 22 | 16 |
| token usage | 10917 | 10489 |

blind 的 2 次失败都发生在 `stale_file_drift`：模型反复读取，直到超过步骤上限。

这些数字只说明当前 3 类合成故障里的小样本现象。不能说成线上成功率、SWE-bench 成绩或通用 100% 成功率。

### 测试结果

- 快速测试：`120 passed, 1 skipped, 28 deselected`，约 52 秒；
- 完整测试：`148 passed, 1 skipped`，耗时 7 分 56 秒；
- 唯一的 skip 是 Windows 没有符号链接权限时的预期处理。

## 四、恢复机制自测

### 能不能讲清动作状态

```text
planned → started → succeeded
                  ↘ failed
                  ↘ reconciled
                  ↘ manual-review-required
```

- [ ] `planned`：准备执行；
- [ ] `started`：已经开始，但不确定是否完成；
- [ ] `succeeded`：明确成功；
- [ ] `reconciled`：恢复时通过当前文件确认其实已经完成；
- [ ] `manual-review-required`：系统无法安全判断，需要用户处理。

### 能不能讲清恢复判断

| 日志和文件状态 | 处理方式 |
| --- | --- |
| `succeeded`，after Hash 也匹配 | 跳过动作，继续 |
| `started`，文件已满足预期结果 | 标记 `reconciled`，不重复执行 |
| `started`，文件仍是 before Hash | 可以安全重试 |
| 文件既不是 before，也不是 after | 转人工确认 |
| 文件摘要 Hash 已过期 | 删除旧信息，重新读取 |
| 工作区或工具签名不一致 | 拒绝重放旧动作 |
| Checkpoint 或 Journal 不兼容、损坏 | 明确失败，不伪装恢复成功 |
| Shell 副作用无法判断 | 转人工确认，不自动重放 |

自测问题：

- [ ] 为什么不能只加载旧 History？
- [ ] 为什么 Checkpoint 不能代替 Action Journal？
- [ ] 为什么文件写入能对账，而任意 Shell 不能？
- [ ] 为什么恢复判断不交给 DeepSeek？
- [ ] `blind_resume` 为什么只能作为实验对照组？

## 五、Context 自测

每个 Context Block 至少包含：来源、来源 Hash、创建时间、优先级、是否受保护、原始长度、最终长度、处理结果和原因。

处理结果有：

- `keep`：原样保留；
- `summarize`：压缩后保留；
- `drop`：因为预算或优先级被删除；
- `stale_rejected`：来源已经变化，旧内容不能再用。

必须能回答：

- [ ] Current Request 和 Recovery Context 为什么要保护？
- [ ] 受保护内容本身超过预算时为什么必须报错？
- [ ] 文件摘要为什么必须保存来源 Hash？
- [ ] 为什么恢复结果要优先于旧 History？
- [ ] Trace 如何解释“删了什么、为什么删”？

## 七、故障备用方案

### 没有网络

- [ ] 优先使用本机 Ollama；
- [ ] Ollama 也不可用时播放完整录屏；
- [ ] 预生成 JSON 只用于说明恢复机制，不冒充实时产品演示。

### Windows 没有符号链接权限

接受测试中的预期 skip，不要求临时开启开发者模式或管理员权限。

### DeepSeek 调用失败

不要现场排查或打印 Key。明确说明这是外部模型请求失败，切换备用方案。

### 模型没有按预期修改

拒绝越界操作，重新强调“只修改 checkout.py”；必要时把最大步骤从 8 调到 12，不降低验收标准。

满足下面 7 项后，不再增加任何功能：

1. Windows 快速测试通过；
2. FakeModel Recovery 演示可重复运行；

4. 能解释 stale 信息为什么不能进入新 Prompt；

7. 简历、实验报告和口头说法完全一致。

最后统一用这段话收口：

> 我没有继续堆功能，而是集中解决 Agent 长任务恢复的一致性问题。工具执行前先写动作日志，恢复时用文件 Hash、后置条件、工作区身份和工具签名做确定性对账。已完成的动作不会重复执行，过期信息不会重新进入上下文，不确定副作用会交给用户。FakeModel 验证状态机，DeepSeek 只做小样本真实模型续跑验证。当前实现是 Windows 单机版本，不等于分布式高可用，但幂等、对账和可审计的思路与生产系统是相通的。
